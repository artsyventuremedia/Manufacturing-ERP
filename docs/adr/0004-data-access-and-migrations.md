# ADR-0004: Data access (Drizzle) and migration strategy

- Status: Accepted (2026-09-25)
- Date: 2026-09-24

## Context

Every request must run inside a transaction that carries the tenant context for RLS (ADR-0005). Ledger postings span modules in one transaction (ADR-0002). PRD §13 requires zero-downtime, backward-compatible migrations across hundreds of pooled tenants and many dedicated or on-prem installs.

## Decision

1. **Drizzle ORM** for schema definitions and typed queries. Raw SQL through Drizzle's `sql` tag for reporting and ledger-critical statements.
2. A single `UnitOfWork` from `@manuling/db` opens the transaction, runs `SET LOCAL app.tenant_id / app.user_id / app.company_ids`, and is passed explicitly to repositories. There is no ambient global connection, and no query can run outside a UoW (lint + runtime guard).
3. **Migrations:** plain SQL files per module schema (`modules/*/migrations`), generated by drizzle-kit then reviewed by hand. They are applied by `@manuling/db` migrate, which tracks versions per schema.
4. **Expand/contract only:** a release may add columns, tables or indexes (built `CONCURRENTLY`). Destructive changes wait until a later release, after code no longer reads the old shape. CI checks migrations for locking operations (squawk).
5. RLS policies and grants are **generated** from table metadata (`tenantScoped: true`), so no table can ship without a policy. CI fails if any table with `tenant_id` lacks RLS.
6. Long data backfills run as Temporal workflows in batches, not inside migrations.

## Consequences

- Explicit transactions make cross-module posting and RLS reliable.
- Hand-reviewed SQL takes more effort per migration but gives safer upgrades for on-prem installs.

## Alternatives considered

Prisma (see ADR-0003), MikroORM (unit of work is attractive, but it is heavier and has a smaller community), TypeORM (maintenance concerns).
