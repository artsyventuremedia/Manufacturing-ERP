## 2. Architectural bottlenecks

| #   | Bottleneck                                           | Where it bites                                        | Mitigation (and trigger to act)                                                                                                                                      |
| --- | ---------------------------------------------------- | ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| B1  | **Single Postgres per cell** (pooled tenants)        | Large tenants, heavy postings, reporting on OLTP      | Cells (ADR-0005): move big tenants to dedicated cells; analytics off OLTP; partition ledgers at ~100 M rows                                                          |
| B2  | Hot rows: stock balances, gapless numbering counters | High-volume goods issues and invoicing in one company | Ledger-first design (balances derived, updated with row locks per item/location); gap-tolerant series where the law allows; gapless only for GST invoices (step 0.7) |
| B3  | RLS overhead on large scans                          | Reports and exports                                   | Tenant-leading composite indexes; reports on replicas/ClickHouse; measured in load tests                                                                             |
| B4  | MRP/APS computation time                             | Plan runs over 50k items                              | Net-change MRP, in-memory computation in a worker, OR-Tools in Python for APS; benchmark in nightly CI                                                               |
| B5  | Kafka ordering vs parallelism                        | Consumers needing per-aggregate order                 | Partition by aggregate id; idempotent consumers with inbox ☑                                                                                                         |
| B6  | Temporal as a critical dependency                    | Approvals and deliveries stall if Temporal is down    | Postgres stays the source of truth (ADR-0015); workflows resume on recovery; alerts on task-queue backlog                                                            |
| B7  | Telemetry volume                                     | IoT at 1 s resolution across many machines            | Separate TimescaleDB cluster, edge aggregation, retention and downsampling                                                                                           |
| B8  | Mobile offline sync conflicts                        | Shop floor and stores with poor connectivity          | Commands (not state) are queued and replayed through the same API; server rules decide; conflict UI (Q10 sync engine)                                                |
| B9  | Modular monolith boundary erosion                    | Modules reaching into each other's tables             | dependency-cruiser rules in CI ☑; contracts packages; context-owned schemas                                                                                          |

## 3. Conflicts between brief v2 and good architecture (and what we do instead)

| #   | Brief v2 says                                                                                                 | Problem                                                                                                                                     | Proposal                                                                                                                                             |
| --- | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| C1  | Phase order puts Finance in Phase 5, after CRM/Sales/Procurement/Inventory (Phase 2) and production (Phase 3) | Perpetual inventory posts to the GL on every movement, and Indian SMBs cannot invoice without GST. Without finance there is no sellable MVP | Keep finance with GST in Phase 1 (current PRD)                                                                                                       |
| C2  | Phases 0–9                                                                                                    | Phase 0 is already built under PRD numbering 0–4; renumbering breaks plans, STATUS.md and ADR references                                    | Keep PRD numbering; map v2 phases onto it ([06](06-product-and-module-map.md) §5)                                                                    |
| C3  | LIFO valuation (§12)                                                                                          | Not permitted under Ind AS 2 or IFRS                                                                                                        | Support FIFO, FEFO (picking), moving average and standard cost; LIFO only as a US GAAP country-pack option later                                     |
| C4  | Separate mobile apps per role (§47)                                                                           | Eight apps multiply release, review and support costs                                                                                       | One mobile app with role-based modes; separate kiosk build for shop-floor terminals if needed                                                        |
| C5  | "No mock functionality" (§92) vs the need to develop against unavailable providers                            | Real providers (SMS, WhatsApp, voice) are not chosen yet                                                                                    | Adapter interface + **sandbox** implementation, labelled `sandbox` in configuration, API responses and the delivery log; never enabled in production |
| C6  | Load tests at 100,000+ concurrent users                                                                       | One database cannot promise this, and an unmeasured claim would mislead                                                                     | 100,000+ is a platform-wide figure across cells; per-cell targets are measured and published                                                         |
| C7  | OpenSearch and ClickHouse from the start (§84)                                                                | Extra clusters for SMB and on-prem with no need yet                                                                                         | Postgres FTS and read replicas first behind ports; add the engines when measured load requires (ADR-0003)                                            |
| C8  | "Every table has created/updated columns" (§86)                                                               | Append-only ledgers and audit must never be updated                                                                                         | Editable tables have them; append-only tables have `created_*` only, and triggers block updates                                                      |
| C9  | Soft delete strategy (§86)                                                                                    | Soft-delete flags leak into every query and conflict with unique keys                                                                       | Lifecycle states (archived, cancelled, reversed); hard delete only for non-business data (idempotency keys, overrides)                               |
| C10 | Voice as a notification channel (§38)                                                                         | Needs a telephony provider and consent rules (TRAI)                                                                                         | Channel slot defined; built after SMS provider choice (Q8)                                                                                           |
| C11 | Demo company "Artsy Manufacturing Pvt Ltd, Mysuru Plant, Industrial Pump"                                     | PRD names "Mysuru Precision Components Pvt. Ltd."                                                                                           | Needs a decision (Q21)                                                                                                                               |

## 4. Security and compliance risks

| #   | Risk                                                                      | Mitigation                                                                                                                         |
| --- | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| S1  | Cross-tenant data leak through a new code path (cache, search, files, AI) | RLS as the base; tenant-prefixed keys everywhere; isolation tests required for every new store ([08](08-security-architecture.md)) |
| S2  | Prompt injection through documents, emails and portal messages            | Untrusted-content labelling, no tool widening, approvals for `execute` tools ([07](07-ai-architecture.md) §8)                      |
| S3  | DPDP Act obligations (consent, data-subject rights, breach notification)  | DSR tooling Phase 1; retention policies; data residency in India regions                                                           |
| S4  | Licence risk in the on-prem installer                                     | Permissive licences only (ADR-0003); legal review before GA (Q12)                                                                  |
